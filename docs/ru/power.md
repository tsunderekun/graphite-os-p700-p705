# Питание, нагрев и режим сна

Документ описывает наблюдения и план проверки питания LG P700. Оценки отделены от измерений; выводы относятся к указанной конфигурации и требуют проверки на целевом устройстве.

## 1. Что снято и чем

| Источник | Что даёт |
|---|---|
| `/sys/class/power_supply/{battery,ac,usb}` | VBAT, «ёмкость», статус, тип источника |
| `/sys/devices/platform/msm-battery/*`, `lge_pm_device/*` | `batt_volt`, `batt_therm`, `chg_therm`, `chg_stat_reg`, `usb_cable`, `chg_current_change` |
| `/sys/devices/system/cpu/cpu0/cpufreq/*` | governor, OPP, `stats/time_in_state` (резидентность по частотам) |
| `/proc/msm_pm_stats` | гистограмма idle: WFI / power collapse / отказы |
| `/proc/stat`, `/proc/<pid>/stat` | загрузка CPU и по процессам |
| `/proc/interrupts` | частота прерываний по источникам |
| `/proc/wakelocks`, `/sys/kernel/debug/wakeup_sources` | wakelock'и и «будящие» устройства |
| `/sys/kernel/debug/suspend_stats` | сколько раз система реально засыпала |
| `/proc/msm_pm_stats`, `/sys/module/pm2/parameters/*` | параметры idle (порог 20 мс, `sleep_time_override`) |
| `/sys/kernel/debug/smsm/state` | биты handshake с модемом (DEM) |
| `/sys/class/leds/lcd-backlight/{brightness,drvstat}` | код яркости LM3530 |
| `/proc/swaps`, `/proc/diskstats`, `/sys/class/mmc_host/*/power` | swap, I/O, runtime-PM карт |
| `dmesg`, `/proc/last_kmsg` | следы прошлого ребута |
| Конфиг ядра (WSL, `config-lg-p700.armv7`) + исходники `lge-kernel-lproj` | что включено/выключено и почему |

Чего нет и не будет без доработки: счётчика тока/энергии, температуры SoC,
`/sys/class/thermal`, управления напряжением ядра из userspace.

Мелочь, но для честности замеров: SSH-сессия через RNDIS (`usb online=1`)
сама стоит 8–15 мА, а снятие снимков `time_in_state`/`/proc/stat` слегка
«будит» CPU. Поэтому все замеры ниже — с этим фоном, а A/B (§8.4) надо
делать с одинаковым фоном.

## 2. Текущая картина — факты

### 2.1. Питание и источник

```
battery: status=Full  present=1  capacity=100  voltage_now=4360000 мкВ  temp=360
ac:      online=0
usb:     online=1
msm-battery: batt_volt=4361  batt_therm=36  chg_therm=64…120 (скачет)
             usb_cable=11  chg_stat_reg=-5  chg_en_reg=-5  chg_current_change=0
lge_pm_device: batt_volt_raw=0  batt_therm_8bit_raw=0  pcb_version=203  msm_batt_level=2
```

Что это значит:

* Телефон висит на **USB-порту ПК** (`usb online=1`, `ac online=0`), т.е. бюджет
  источника — **500 мА / 2.5 Вт**, а не 700 мА «зарядника».
* АКБ нет: `batt_volt_raw=0`, `batt_therm_8bit_raw=0` — сырые АЦП модема пустые.
  `voltage_now = 4.36 В` при `voltage_max_design = 4.2 В` — это **не напряжение
  банки**, а плавающий рельс VBAT: charger IC в CV-режиме, стягивать его нечему.
* `batt_therm = 36.0 °C` **не меняется вообще** (проверено 15 минут) — заглушка,
  а не измерение. `chg_therm` скачет 64…120 — сырой АЦП без калибровки.
  **Достоверной температуры на устройстве нет.**
* `chg_stat_reg = -5`, `chg_en_reg = -5` — регистры charger IC через RPC не
  читаются; `usb_cable = 11` — тип кабеля не определён (та же болезнь, что
  детект джека). Следствие: **тока заряда, лимита и режима CC/CV мы не видим**,
  и телефон, скорее всего, всегда считает источник «USB-PC» (500 мА).

### 2.2. Что реально запущено

```
mode=player, но: Xorg=3274, openbox=3319, tint2=3321, fbpan-ng=3307, lp7player НЕТ
mpd=1427 (volume 5 %, ничего не играет), wpa_supplicant=1487, lgjack=1517
wlan0 associated 2.437 ГГц, 52 Мбит/с, Tx-Power 17 dBm
```

То есть телефон сейчас в **худшем по питанию состоянии**: X с паноратором на
10 Гц, экран горит (подсветка 200/255), плеера нет, музыка не играет. Это остаток
теста `session-desktop` (по `DESKTOP-STATUS.md` его не убирали). Учитывать при
чтении замеров: цифры ниже — это «X простоя», а не «плеер».

### 2.3. CPU и governor

```
scaling_governor=ondemand   scaling_cur_freq=1000000   max=1000000   min=61440
sampling_rate=50000  up_threshold=95  hispeed_freq=1000000  down_differential=3
```

`hispeed_freq = 1 ГГц` = максимум: любой всплеск нагрузки > 95 % швыряет ядро
сразу на 1 ГГц.

Резидентность (`time_in_state`, 30-секундное окно, HZ=100):

| Частота | Время | Доля |
|---|---|---|
| 1 000 МГц | 1908 тиков | **62 %** |
| 600–900 МГц | 190 | 6 % |
| 480 МГц | 165 | 5 % |
| 320 МГц | 171 | 6 % |
| 245 МГц | 210 | 7 % |
| 122 МГц | 106 | 3 % |
| 61 МГц | 321 | 10 % |

За всё время работы (95 мин) — 57 % на 1 ГГц. Для «простаивающего» телефона
это ненормально; виновник найден ниже.

### 2.4. Кто жжёт: fbpan-ng

Замер по `/proc/<pid>/stat` (10 с, 1045 тиков всего):

```
fbpan-ng   467 тиков user  = 45 % одного ядра непрерывно
kworker/0:1 13, TX_Thread 8, остальные < 5
```

`fbpan-ng` — панораматор X-сессии, 10 Гц × 480×800×16 бит ≈ 7.7 МБ/с копирования
через CPU (в `DESKTOP-STATUS.md` он же назван причиной нагрузки). Один он
объясняет и 1 ГГц-резидентность, и нагрев. Плеер (`lp7player`) в fb-режиме
рисует только по событию и 1 раз в секунду опрашивает MPD — на два порядка
дешевле.

### 2.5. Idle: power collapse не наступает ни разу

`/proc/msm_pm_stats` (за 95 мин):

```
idle-request: 160 302 входа, 2662 с
idle-wfi:     160 302 входа, 2193 с        <-- всё время только WFI
idle-power-collapse: count 0, total 0
idle-standalone-power-collapse: count 0
```

Гистограмма запрошенного сна: 84 600 входов в диапазоне 4–16 мс, 31 000 —
16–64 мс, всего 51 вход > 256 мс. Порог входа в power collapse —
`/sys/module/pm2/parameters/idle_sleep_min_time = 20000000` (20 мс), т.е. нужен
следующий таймер дальше 20 мс.

Причины (обе видны в коде `arch/arm/mach-msm/pm2.c:arch_idle()`):

1. **Окно простоя почти всегда < 20 мс.** Прерывания: `msm-sdcc (pio)` (irq 26)
   ~120/с, dg_timer ~85/с, msmdatamover ~9/с, msm_hsusb ~3/с, smd ~0.8/с, плюс
   10 Гц паноратор. Итог — «дёрганый» idle 4–16 мс. Какой именно хост висит на
   irq 26 (eMMC или SDIO), пока не установлено — это отдельная задача
   (blktrace/iotop), но на вывод это не влияет.
2. **Проверка wakeup-способности прерываний** (`msm_irq_idle_sleep_allowed()`):
   если хоть одно активное прерывание не умеет будить из PC, PC запрещён целиком.
   На порте это очень вероятно (тач, SDCC-poll, ISP).

Handshake с модемом при этом **не** мешает: `CONFIG_MSM_IDLE_WAIT_ON_MODEM=0`
(не ждём модем), а бит `DEM_MASTER_SMSM_READY` в `SMSM_POWER_MASTER_DEM`
поднят (`/sys/kernel/debug/smsm/state`, entry 6 = `0x11` = RUN|READY).
Модем «готов», но PC всё равно не включается.

**Вывод: «спящего» режима нет.** Даже с выключенным экраном ядро остаётся в WFI
на 61 МГц с поднятыми рельсами. Это и есть главный резерв.

### 2.6. D-состояния и RPC

```
krtcclntd, kbatteryclntd, khsclntd, voicememo_rpc, krtcclntcbd, kbatteryclntcbd
   state=D  wchan=__msm_rpc_read
loadavg = 7.8…8.6  (два D-потока = +~2 к loadavg, остальное — реальная нагрузка)
```

В `ps` их «нет» только потому, что busybox `ps` не показывает D-потоки;
через `/proc/*/stat` они видны. Wakelock при этом **не держат** (в
`/proc/wakelocks` `active_since = 0` у всех), т.е. сами по себе suspend не
блокируют — но говорят о полуживом RPC: модем не отвечает на часть запросов.

### 2.7. Экран, подсветка, панель

```
lcd-backlight: brightness=200/255   LM3530: full-scale 20 мА, exponential,
               intensity=121/127 (по drvstat)
button-backlight: 255 (горит)
fb0: 480x800, 16 bpp, msm_fb_type = "mipi dsi video panel", state=0
mipi_lg4573b.769/lcd_onoff — есть (rw), панель сейчас включена
```

Важно: «погасить экран» в плеере = записать `0` в
`/sys/class/leds/lcd-backlight/brightness` (`lp7player.cpp:712`). **Панель и DSI
при этом продолжают работать** — video mode не останавливается, `FBIOBLANK`
никто не зовёт. То есть «лок» экономит только подсветку (40–65 мА), но не
10–20 мА панели+DSI.

`FBIOBLANK`/`lcd_onoff` трогать пока нельзя: в `dmesg` и `last_kmsg` виден
цикл `mipi_lg4573b_chip_lcd_off` → `lcd_on` каждые ~50–350 мс с
`esd_int_en_wq_handler` и `mdp_block_power_cnt: multiple power-off request`.
Это тот самый баг `msm_fb`, из-за которого ребутило под X (ядро #23 его
смягчило, но не убрало).

### 2.8. Карты, swap, Wi-Fi

```
mmc0 (eMMC) runtime=suspended   mmc1 (SD) runtime=suspended
mmc2 (SDIO/Wi-Fi) runtime=ACTIVE     <- не засыпает никогда
swap: /swapfile 256 МБ на eMMC, использовано 0, swappiness=60
```

`mmc2` активен из-за патча `mmc_poll.patch`
(`MMC_CAP_NEEDS_POLL` для `pdev->id == 2`) — без него Wi-Fi вообще не работал
(нет линии SDIO-IRQ). Побочный эффект: хост опрашивается ~1 Гц, LDO Wi-Fi
(`ldo05/06/19/11`) не отключаются, SDIO-хост не уходит в runtime-suspend.
Управления power-save у драйвера нет (`iwconfig` не показывает Power Management,
`iw` в системе отсутствует, у модуля `wlan` только `driver_mode`/`ioctl_debug`).

### 2.9. Что было при прошлом ребуте

```
/proc/cmdline: lge.reboot=<null>
/proc/last_kmsg (903 Б): lcd_off/lcd_on петля + "No errors detected"
suspend_stats: success 0, fail 0   <- suspend не пробовали ни разу
```

Паники нет, LG-парсер ошибок не нашёл, причина ребута бутлоадером не записана.
Это укладывается в **аппаратный сброс по питанию**, а не в софтовый краш
(см. §4).

Сверка с реальностью: сейчас телефон в состоянии D; 0.9–1.2 Вт для корпуса
4.3″ — это заметное тепло, что и наблюдается на ощупь. Цифрами это не
подтвердить: достоверной температуры на устройстве нет (см. §2.1), нужен
ИК-термометр или внешняя термопара. Для сравнения: АКБ BL-44JH
(≈1540 мА·ч) в состоянии A дала бы ~6 ч, в состоянии D — ~5 ч.

Что из этого **факт**: состав процессов, 45 % fbpan-ng, 62 % на 1 ГГц, PC=0,
mmc2 active, яркость 200, отсутствие температуры. Что **оценка**: любая цифра
в мА — её надо подтвердить внешним ваттметром (§8).

## 4. Без АКБ от USB: почему ребутит

### 4.1. Механизм

1. **Нет буфера.** Банка АКБ — это малое внутреннее сопротивление (десятки мОм)
   плюс сотни микрофарад. Без неё VBAT держится только выходной ёмкостью
   charger IC (единицы–десятки мкФ) и кабелем до порта.
2. **Нет CV-петли.** `voltage_now = 4.36 В` при design max 4.2 В: заряжать
   нечего, рельс плавает у верхней границы. Запас до UVLO есть, но он
   «мягкий» — любой шаг нагрузки просаживает VBAT на сотни мВ.
3. **Источник 500 мА и он не бесконечный.** Порт ПК отдаёт 500 мА; при
   превышении растёт падение на кабеле (1 м тонкого кабеля — 0.3–0.5 Ом,
   т.е. 150–250 мВ при 500 мА), дальше порт уходит в защиту.
4. **Пики.** Подсветка на старте (inrush boost), пакет Wi-Fi на 17 dBm
   (+150–250 мА на единицы мс), шаг CPU на 1 ГГц, MDP/DSI.
5. Итог: VBAT на мгновение проваливается ниже порога PMIC → **hardware reset**.
   Паники нет, `last_kmsg` чист, `lge.reboot=<null>` — ровно то, что мы видим.

Порог по среднему току для текущей конфигурации (ПК-порт, без АКБ) —
эмпирически **≈ 400 мА**: состояние A/C живёт, D на грани, E — ребут через
десятки секунд. Совпадает с тем, что «X сам перезагрузился через ~30 с».

### 4.2. Как проверить (без ваттметра и с ним)

Без ваттметра, косвенно:
* `cat /proc/last_kmsg` после ребута — если снова «No errors detected» и нет
  паники, это питание, а не софт;
* повторяемость: ребут ловится нагрузкой (X + паноратор + Wi-Fi Tx), а не
  временем;
* `dmesg | grep -i 'vbus\|chg'` перед ребутом — если контроллер успевает
  ругнуться на VBUS, это источник.

С ваттметром (правильно): USB-тестер в разрыв, смотреть **просадку напряжения**
при пиках, а не только средний ток. Просадка ниже 4.75 В на входе = кабель/
порт виноваты.

### 4.3. Как смягчить (по убыванию эффекта)

1. **Питать от зарядника 5 В / 1.5–2 А** (и коротким толстым кабелем). Даже
   если телефон продолжит считать источник «USB» и просить 500 мА, зарядник
   отдаст их без просадки. Это самое дешёвое и самое эффективное.
2. **Поставить АКБ** (хотя бы старую рабочую BL-44JH) — снимает проблему
   полностью: появляется буфер и CV-петля. Для «карманного плеера» это
   обязательный шаг.
3. **Держать нагрузку ниже бюджета**, пока АКБ нет:
   * яркость ≤ 150 вместо 200 (экономия 15–25 мА и минус пик inrush);
   * `scaling_max_freq = 800000` (или 600000) в простое;
   * Wi-Fi выключать, когда не нужен;
   * не держать X с панораматором 10 Гц «просто так» (см. §7);
   * не запускать браузер одновременно с X-шеллом и Wi-Fi Tx.
4. **Аппаратная заплатка для стенда** (по желанию владельца): электролит
   470–1000 мкФ low-ESR + керамика 10 мкФ на контакты BAT+/BAT− — имитация
   буфера АКБ. Только руками, с проверкой полярности; риск броска тока при
   подключении.
5. **Предупреждение в UI**: если `ac/online=0 и usb/online=1` — рисовать в
   шторке «Питание от ПК: не более 500 мА» и автоматически резать яркость/
   частоту. (Плитка «Питание» уже есть в макете шторки.)

## 5. Сон и suspend

### 5.1. Что включено в ядре

| Опция | Значение | Смысл |
|---|---|---|
| `CONFIG_MSM7X00A_SLEEP_MODE_POWER_COLLAPSE_SUSPEND` | y | suspend = power collapse с выключением XO |
| `CONFIG_MSM7X00A_IDLE_SLEEP_MODE_POWER_COLLAPSE` | y | idle тоже *должен* уметь PC |
| `CONFIG_MSM_IDLE_WAIT_ON_MODEM` | 0 | не ждём модем перед PC (правильно) |
| `CONFIG_MSM_SLEEP_TIME_OVERRIDE` | y | `pm2/sleep_time_override` — ограничитель сна |
| `CONFIG_MSM_PM_TIMEOUT_HALT` | y | при таймауте handshake — `printk` + `for(;;);`: вечный busy-loop, не возврат |
| `CONFIG_WAKELOCK`, `WAKELOCK_STAT`, `USER_WAKELOCK` | y | wakelock'и есть, `/sys/power/wake_lock` |
| `CONFIG_EARLYSUSPEND`, `FB_EARLYSUSPEND` | y | early-suspend для fb |
| `CONFIG_PM_SLEEP`, `PM_RUNTIME` | y | `/sys/power/state = mem` |
| `CONFIG_RTC_DRV_MSM` + `RTC_INTF_ALARM_DEV` | y | `/dev/rtc0`, `/dev/alarm` есть |
| `CONFIG_THERMAL` | **n** | термозащиты нет вообще |
| `CONFIG_USB_OTG_WAKELOCK` | n | USB не держит wakelock (хорошо) |
| `CONFIG_LGE_BATTERY_SUSPEND_RESUME` | y | батарейный драйвер не вешает early-suspend |

В платформенных данных (`board-msm7x27a_u0.c`) режимы POWER_COLLAPSE и
POWER_COLLAPSE_NO_XO_SHUTDOWN имеют `suspend_enabled = 1` — то есть
`echo mem > /sys/power/state` формально разрешён и полезет в реальный
power collapse с handshake к модему.

### 5.2. Что его блокирует и чем это грозит

* **Idle-PC не работает** (0 входов за 95 мин, §2.5) — значит либо окно < 20 мс,
  либо какое-то IRQ помечено «не будит». Это надо разделять отладкой
  (`pm2/debug_mask`), а не догадками.
* **Suspend ни разу не пробовали**: `suspend_stats: success 0, fail 0`.
* **Будящих устройств всего три** (`/sys/kernel/debug/wakeup_sources`):
  акселерометр `3-0030`, `msm_hsusb_host.0`, `msm_otg`. **Клавиши, тач,
  `7k_handset` и RTC не зарегистрированы как wakeup-источники** — у них
  вообще нет атрибута `power/wakeup`.
* Практический вывод: если сейчас послать `mem`, телефон уйдёт в PC и **не
  проснётся ни от кнопки, ни от тача, ни по будильнику** — только USB-событие
  или длинное удержание Power (аппаратный сброс PMIC). Без АКБ «выдернуть
  батарейку» нельзя.
* Отдельная засада: `CONFIG_MSM_PM_TIMEOUT_HALT=y`. Если handshake с модемом не
  сложится, `msm_pm_timeout()` печатает `halting` и уходит в `for (;;);` —
  бесконечный busy-loop **на максимальной частоте** (греется, жрёт ток, ничего
  не отвечает). Ни `CONFIG_MSM_RPC_WATCHDOG`, ни `RESET_CHIP` не включены.
  Выход — только длинное нажатие Power. Поэтому suspend на этом ядре — не
  «попробовать и посмотреть», а отдельная работа с обязательным откатом.

### 5.3. Экран выключен ≠ suspend

Сейчас «лок» — это `brightness=0` (`lp7player.cpp:712`) плюс игнор ввода.
Процессор продолжает крутить `select()` с таймаутом 200 мс (5 пробуждений/с),
панель остаётся в video mode. То есть **экономится только подсветка**.
Реальный «сон» в терминах энергии — это (а) панель off, (б) PC/WFI без
1 ГГц, (в) Wi-Fi без опроса, (г) в идеале — suspend.

### 5.4. Безопасный тест suspend (только с владельцем рядом, не сейчас)

`CONFIG_MSM_SLEEP_TIME_OVERRIDE` даёт страховку: значение в секундах один раз
подставляется как максимальное время сна, после чего AP **сам** просыпается по
таймеру, даже если нет ни одного wakeup-источника.

```sh
# НЕ ЗАПУСКАТЬ без человека рядом и без внешнего ваттметра
echo 20 > /sys/module/pm2/parameters/sleep_time_override
echo mem > /sys/power/state
# ожидание: телефон спит ~20 с и сам возвращается; проверить
cat /sys/kernel/debug/suspend_stats     # success: 1
cat /proc/uptime                        # uptime НЕ прыгнул (это suspend, не ребут)
```

Если не вернётся — длинное удержание Power (8–10 с) сбрасывает PMIC. План Б:
не трогать suspend до того, как в ядре появятся wakeup-источники (см. §10, фаза 3),
и до того, как `CONFIG_MSM_PM_TIMEOUT_HALT` заменится на `..._RESET_CHIP` в
тестовой сборке — иначе таймаут handshake даёт вечный `for(;;);`.

## 6. Governors, частоты, напряжения

* Сейчас: `ondemand`, `sampling_rate=50 мс`, `up_threshold=95`,
  `hispeed_freq=1 ГГц`, `down_differential=3`, `sampling_down_factor=1`.
* Доступно без пересборки: `ondemandX hyper wheatley smartmax dancedance badass
  AssWax SmartassH3 smartassV2 interactive conservative userspace powersave
  lionheart ondemand performance`. `adaptive`/`lulzactive` выключены в конфиге
  (`CPU_FREQ_GOV_ADAPTIVE/LULZACTIVE = n`).
* OPP (из `acpuclock-7627.c`, таблица 1008 МГц): 61 / 122 / 245 / 320 / 480 /
  600 / 1008 МГц, уровни VDD `2,3,4,5,6,7`. Точные вольты задаёт AMSS, наружу
  они не выведены (`REGULATOR_USERSPACE_CONSUMER` выключен).
  В коде есть оговорка: «v1.0 7x27a не умеет переключать VDD» — на ревизии
  silicon < 1.0 напряжение не меняется вместе с частотой, и экономия от
  снижения частоты меньше ожидаемой. Проверять по факту (см. §8).
* CPR включён (`/sys/module/msm_cpr/enable = Y`), но на 7x27A он, скорее всего,
  no-op.
* **Термозащиты нет**: `CONFIG_THERMAL=n`, `/sys/class/thermal` пуст, датчика
  температуры SoC нет. Единственная защита — собственный OTP PMIC, а его
  срабатывание выглядит как ребут (совпадает с нашим случаем).

Политика по режимам:

| Режим | governor | max | min | Комментарий |
|---|---|---|---|---|
| Плеер, экран вкл, играет | `smartassV2` или `interactive` | 600–800 МГц | 61 | 1 ГГц не нужен: UI 1 Гц |
| Плеер, лок | `powersave`/`conservative` | 320–480 МГц | 61 | MPD/ALSA сами просыпаются |
| X / шелл, простой | `interactive` | 600 МГц | 61 | при панораторе 10 Гц всё равно 1 ГГц |
| X + браузер | `ondemand` | 1008 МГц | 61 | единственный сценарий для 1 ГГц |
| На USB-порту ПК | любой | 600 МГц | 61 | страховка от ребута |

`ondemand` с `hispeed_freq=1 ГГц` для этого телефона — худший выбор: он
превращает любой чих в 1 ГГц. Минимум — поставить `hispeed_freq=480000` и
`up_threshold=98` (это правка sysfs, обратимая, без пересборки).

## 7. Политика питания (что должно быть в UI/сервисах)

1. **Авто-дим**: нет ввода 10 с → яркость 150 → 90 (плавно, 2–3 шага).
2. **Авто-лок**: нет ввода 30 с **и** MPD на паузе → лок (подсветка 0).
   Если музыка играет — экран гасить можно, но плеер не должен останавливаться.
3. **Лок = подсветка 0 + (после фикса msm_fb) панель в sleep + CPU max 480 МГц.**
   Пока фикса нет — только подсветка, панель оставить живой.
4. **Экран при воспроизведении**: разрешать гасить экран через 15 с (как сейчас
   на экране лока), но `refresh_state()` не звать, пока лок (в коде уже так:
   `lp7player.cpp:1561`). Добавить: в локе `select()` с таймаутом 1 с вместо
   200 мс — минус 4 пробуждения/с.
5. **Яркость по умолчанию 150**, не 200. Максимум 255 — только вручную и с
   предупреждением на USB-порту.
6. **Клавишная подсветка**: авто (5 с) — уже есть; в локе всегда 0 — уже есть.
7. **Wi-Fi в простое**: выключать модуль (`rmmod wlan` + `ifdown wlan0`), когда
   сети не нужны: это гасит SDIO-poll, LDO Wi-Fi и сам радио-тракт (15–40 мА).
   В шторке — плитка Wi-Fi (уже в макете). Автоотключение через 10 мин без
   соединений — опционально.
8. **Swap**: `/swapfile` 256 МБ на eMMC при 400 МБ RAM — плохая идея (износ +
   латентность + питание). Лучше `zram` (сжатие в RAM) или вообще без swap,
   а плеер и шелл держать в пределах 60–80 МБ.
9. **USB-порт ПК**: баннер в шторке + авто-лимит (яркость 150, max 600 МГц,
   Wi-Fi off) пока `ac=0, usb=1`.
10. **Таймеры/логи**: убрать спам `msm_batt_update_psy_status: enter/exit`
    (1 Гц в dmesg → запись в лог на eMMC); в идеале — `pr_debug`.

## 8. Как измерять потребление без ваттметра (и с ним)

### 8.1. Что доступно на телефоне (и чего нет)

| Метрика | Есть? | Где |
|---|---|---|
| Напряжение VBAT | да (но без АКБ — плавающий рельс) | `power_supply/battery/voltage_now`, `msm-battery/batt_volt` |
| Ток/мощность | **нет** | — (нет `current_now`, `power_now`, `charge_counter`) |
| Заряд/ёмкость | «да» (от AMSS, без АКБ — фикция 100 %) | `capacity` |
| Температура | **нет достоверной** | `batt_therm` = константа, `chg_therm` = шум |
| Резидентность частот | да | `cpufreq/stats/time_in_state` |
| Idle-статистика (WFI/PC) | да | `/proc/msm_pm_stats` |
| Suspend-статистика | да | `/sys/kernel/debug/suspend_stats` |
| Частота прерываний | да | `/proc/interrupts` |
| Per-process CPU | да | `/proc/<pid>/stat` |
| Runtime-PM устройств | да | `.../power/runtime_status` |

Итого: **абсолютные ватты софтом не измерить.** Можно измерить структуру
нагрузки (кто, сколько, на какой частоте, спит ли), а ватты — только внешним
тестером.

### 8.2. Снимок для A/B (read-only, кладём на телефон и запускаем)

```sh
#!/bin/sh
# power-snapshot.sh — один блок цифр для сравнения сценариев
echo "ts=$(date -u +%s) up=$(cut -d' ' -f1 /proc/uptime)"
echo "bl=$(cat /sys/class/leds/lcd-backlight/brightness) vbat=$(cat /sys/class/power_supply/battery/voltage_now)"
echo "ac=$(cat /sys/class/power_supply/ac/online) usb=$(cat /sys/class/power_supply/usb/online)"
echo "freq=$(cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq) gov=$(cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor)"
cat /sys/devices/system/cpu/cpu0/cpufreq/stats/time_in_state
head -1 /proc/stat
grep -A1 'idle-power-collapse' /proc/msm_pm_stats | head -2
cat /sys/class/mmc_host/mmc2/device/power/runtime_status
wc -l < /sys/kernel/debug/wakeup_sources
```

Дальше — два снимка с интервалом 60 с, разница `time_in_state` даёт среднюю
частоту, разница `/proc/stat` — загрузку, разница счётчиков `idle-*` — спал ли
процессор. Это дешёвая замена ваттметру для сравнения «до/после».

### 8.3. Что просить у владельца

1. **USB-тестер** (5 В/3 А, с напряжением и мА·ч; лучше с логом) — главный
   инструмент. Без него бюджет остаётся оценкой.
2. **Зарядник 5 В / 1.5–2 А** и короткий толстый кабель.
3. **АКБ BL-44JH** (живая или хотя бы держащая 10 минут) — снимает весь класс
   проблем с просадками и включает честные `current_now`/температуру.
4. По желанию: ИК-термометр (или просто «на ощупь» + время до ребута) — для
   калибровки «нагрев ↔ нагрузка».

### 8.4. Программа замеров (по одному изменению за раз, 60 с на точку)

| № | Сценарий | Что доказывает |
|---|---|---|
| 1 | Плеер, лок, пауза, Wi-Fi off | базовый «сон» (сейчас ~120 мА оценка) |
| 2 | Плеер, экран 200, пауза | цена экрана |
| 3 | Плеер, экран 255 vs 0 | цена подсветки (разница = LM3530) |
| 4 | Плеер, играет в наушники vs пауза | цена аудио-тракта |
| 5 | Wi-Fi on vs `rmmod wlan` | цена SDIO-poll + радио |
| 6 | X простой vs плеер простой | цена fbpan-ng (ожидаем +150–200 мА) |
| 7 | X, паноратор 10 Гц vs 2 Гц vs «по damage» | главный рычаг X |
| 8 | CPU pinned 61/245/480/1008 МГц (`cpufreq-set -f`) | вольт-частотная кривая, проверка «v1.0 без VDD» |
| 9 | Нагрузка до ребута (бинарный поиск) | реальный потолок на ПК-порту |

## 9. Риски

| Риск | Вероятность | Чем грозит | Как снижать |
|---|---|---|---|
| `echo mem` без wakeup-источников | высокая | телефон не проснётся, только сброс кнопкой | тест только с `sleep_time_override` и человеком рядом |
| Таймаут handshake в suspend (`PM_TIMEOUT_HALT`) | средняя | `for(;;);` на 1 ГГц: вечный висяк + нагрев, спасение — только Power | не тестировать без нужды; в сборке включить `RESET_CHIP` вместо `HALT` |
| Снижение `idle_sleep_min_time` | средняя | PC с «плохим» пробуждением → зависание | по шагам 20→10→5 мс, с логом `pm2/debug_mask` |
| `FBIOBLANK`/`lcd_onoff` на локе | высокая | петля `lcd_off/lcd_on` и ребут (уже видели) | только после фикса `msm_fb`, тест 10 мин |
| Яркость 255 / X + браузер на USB-порту | высокая | ребут по просадке VBAT | лимиты + баннер + зарядник |
| Перегрев без термозащиты | средняя | OTP PMIC = внезапный ребут, деградация | не держать 1 ГГц постоянно; IR-термометр |
| `rmmod wlan` в неудачный момент | низкая | потеря Wi-Fi до перезагрузки, D-состояния | выгружать только при `ifdown`, проверять `lsmod` |
| Swap на eMMC | низкая | износ карты, лаги | убрать swapfile / zram |
| Правки в ядре (wakeup, thermal) | средняя | новый ребут/висяк на ровном месте | отдельная сборка + KNOWN-GOOD откат |

## 10. План по шагам

### Фаза 0 — база (0.5 дня, без изменений на телефоне)

1. Зафиксировать текущее состояние этим документом + снимком §8.2.
2. Положить `power-snapshot.sh` в `notes/` (запуск по SSH, read-only).
3. Убрать расхождение «`mode=player`, а работает X»: решить, что считается
   штатным состоянием (сейчас телефон живёт в самом дорогом режиме).
4. Попросить у владельца USB-тестер / зарядник / АКБ.

### Фаза 1 — политика плеера (1–2 дня, userspace, без пересборки ядра)

1. Яркость по умолчанию 150; дим до 90 через 10 с; лок через 30 с (если пауза).
2. `scaling_max_freq`: 800 МГц обычно, 480 МГц в локе; `hispeed_freq=480000`,
   `up_threshold=98` (или governor `smartassV2`).
3. В локе: `select()` 1 с вместо 200 мс, не дёргать MPD.
4. Плитка/баннер «USB-PC 500 мА» + авто-лимиты при `ac=0, usb=1`.
5. Выключатель Wi-Fi в шторке = `ifdown` + `rmmod wlan` (+ обратно).
6. Замеры 1–5 из §8.4. Ожидаемый эффект: **−60…90 мА** в локе, **−30 мА** на
   экране, без риска для стабильности.

### Фаза 2 — X/шелл (2–3 дня)

1. `fbpan-ng`: панорамировать **только по damage** (или 2 Гц). Это −45 % CPU и
   возврат к 245–480 МГц в простое. Самый большой единичный выигрыш.
2. Для X: max 600 МГц в простое, 1 ГГц только при скролле/браузере.
3. Не держать X и плеер одновременно; `restore-player.sh` должен гасить X.
4. Замер 6–7. Ожидаемо: состояние D → 0.6–0.8 Вт.

### Фаза 3 — ядро, одна сборка (3–5 дней, maintenance-окно)

1. Добить `msm_fb` blank (условие `cont_splash_done`, не звать unblank, если
   панель уже включена) — тогда `FBIOBLANK` на локе станет безопасным:
   −10–20 мА и панель реально спит.
2. `msm_batt_update_psy_status`: спам 1 Гц → `pr_debug` (минус запись в лог).
3. Зарегистрировать wakeup-источники: keypad (`gpio_kp`/`7k_handset`), тач,
   `rtc-msm` (`device_init_wakeup`). Тогда suspend станет осмысленным.
   В тестовой сборке поменять `PM_TIMEOUT_HALT` → `PM_TIMEOUT_RESET_CHIP`
   (сброс чипа вместо вечного `for(;;);`).
4. Диагностика PC: `echo 1 > /sys/module/pm2/parameters/debug_mask`, снять
   `allow power_collapse: 0/1` и понять, что именно режет (окно < 20 мс или IRQ).
   Затем, если окно — снизить `idle_sleep_min_time` до 10/5 мс.
5. Опционально: убрать `MMC_CAP_NEEDS_POLL` для mmc2, когда Wi-Fi выгружен
   (или сделать poll адаптивным).
6. Тест suspend строго по §5.4, с `sleep_time_override` и ваттметром.

### Фаза 4 — «сон» как продукт (после фазы 3)

1. Лок → панель off + max 480 МГц + (через N минут) suspend.
2. Будильник плеера на `rtc0`/`/dev/alarm` (просыпаться к таймеру сна).
3. Автопробуждение по кнопке/тачу — обязательно проверить 20+ циклов.
4. Целевые цифры: лок 40–80 мА, suspend 3–8 мА, экран+плеер 180–250 мА.

## 11. Три главных вывода

1. **Телефон не спит и не может спать: за 95 минут — ноль power collapse и ноль
   suspend, только WFI.** Причина не в конфиге сна (он включён и корректен), а
   в том, что окно простоя почти всегда < 20 мс (10 Гц паноратор + ~120 IRQ/с)
   и/или какое-то прерывание не умеет будить из PC. Пока это так, весь бюджет
   определяется «включённым экраном и работающим ядром», и главный рычаг —
   убрать `fbpan-ng` с 10 Гц (45 % ядра) и 1 ГГц-резидентность (62 %).

2. **Спонтанный ребут под X — это просадка VBAT, а не софт.** Без АКБ нет
   буфера и нет CV-петли (рельс 4.36 В плавает), источник определяется как
   USB-PC (500 мА), а X с паноратором даёт 220–300 мА средних и пики в
   полампера; паники нет, `last_kmsg` чист, `lge.reboot=<null>`. Лечится в
   таком порядке: зарядник 1.5–2 А + короткий кабель → АКБ → лимиты
   яркости/частоты/Wi-Fi → предупреждение в UI.

3. **Suspend пока не цель, а R&D-задача.** Будящих устройств всего три
   (акселерометр, USB, OTG); клавиши, тач и RTC не зарегистрированы, поэтому
   `echo mem` — это билет в один конец до длинного нажатия Power. Сначала
   политика «экран выключен = подсветка 0 + панель off + 480 МГц + Wi-Fi off»
   (это 80 % выигрыша без риска), и только потом — `device_init_wakeup` для
   клавиш/тача/RTC и тест suspend через `sleep_time_override`.
