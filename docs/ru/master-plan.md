# MASTER-PLAN — graphite shell / LG P700

Срез: 26.11.2026. Shell загружается на P705; статус ниже сверён с STATUS.md.

## Вердикт

Graphite работает как Xlib-shell. На устройстве проверены задачи с двумя слотами, PIN, шторка, power policy (подсветка), файловые сценарии и EPUB2/3. Host QA и два 30-минутных soak прошли; это не полный release gate. Viewer и clock/timer пока host-only. Ограничения: нет телефонии, камеры, видео, GPU, Bluetooth, GPS и подтверждённого suspend; PIN не шифрует данные.

Оценка 10–13 рабочих дней по READER-V2; soak 60 минут после интеграции. EPUB только после v1.
2. **Задачи и уведомления**: сначала владелец решает multi-app policy. Затем apphost task list/suspend/resume, не более 3–4 задач и 2 тяжёлых; только после этого `tasks` UI и системная notify-модель. ## Открытые решения владельца (актуальные ограничения)

1. **Multi-app policy:** нужно ли держать dillo/xterm живыми в фоне? Если да — лимит 3–4 задачи, Home сворачивает, Back закрывает; какие приложения считаются тяжёлыми и допускается ли вытеснение?
2. **USB продукт:** нужен ли вообще USB mass storage в UI, и достаточно ли образа 256 MiB, или требуется доступ к SD (с остановкой MPD и риском FAT)? По умолчанию оставить только RNDIS.
3. **Lock/PIN:** нужен ли PIN в ближайшем продукте? До решения lock считать экранным барьером без аутентификации, не обещать защиту данных.
4. **Video go/no-go:** выделяется ли отдельное supervised device-окно и стабильное питание на pan gate? Без PASS и отдельного одобрения видео остаётся отложенным.
5. **Release boundary:** какой результат считать ближайшим релизом — надёжный shell поверх существующего плеера или shell + Reader v1? От этого зависит последовательность и объём P1.

## Приёмка «похоже на мобильную ОС» — устройство

Проводить на известном ядре/образе, с зафиксированными `uname -a` и `boot_id`; короткая функциональная проверка — на АКБ или устойчивом источнике, soak — только после smoke и с rollback. Любой новый reset, OOM, user-space D, fb timeout или display storm — FAIL/стоп.

1. Холодная загрузка: shell запускается автоматически, до 90 с доступен локальный UI/SSH; режим и процессы соответствуют друг другу, X и fb-player не конкурируют.
2. Пуск: открытие плеера, приложений и настроек, возврат Back/Home; ни одного пустого/фальшивого пункта приложения.
3. Клавиши: Back/Menu/Home/Search, Power коротко/долго, Volume коротко/удержание; без повторного события/залипания.
4. Жесты: edge-back, свайп пивота, открытие/закрытие shade; вертикальный drag не меняет слайдер, горизонтальный drag работает.
5. Статус-бар: корректные Wi-Fi/USB/наушники/заряд; USB не отображается фиктивно; три темы не ломают центровку/контраст.
6. Плеер: play/pause/next/prev/seek, смена трека и обложки, очередь и библиотека; MPD disconnect/reconnect не вешает shell.
7. Файлы: открыть/скроллить каталог, выбрать несколько, copy/move/delete/rename; отмена/ошибка честны, файл не теряется.
8. Заметки: создать/открыть, вставить в середину, undo/redo, автосейв; перезапуск не оставляет обрезанный файл.
9. Внешние приложения: xterm и dillo запускаются как uid 10000; OSK вводит RU/EN; Back скрывает OSK прежде закрытия приложения.
10. Shell recovery: падение/закрытие внешнего окна возвращает управляемый экран; нет зомби; fallback при нестарте X остаётся доступен.
11. Память и отзывчивость: одна тяжёлая задача; 30 минут работы без OOM/user D, RSS стабилен, тапы/Back не блокируются сетевым timeout.
12. Lock: Power блокирует ввод и гасит подсветку, музыка продолжает; Power/разрешённый жест возвращает экран; никаких panel blank/suspend в этой приёмке.
13. SD/звук/сеть: SD монтируется, библиотека доступна, наушники переключаются, RNDIS и Wi-Fi восстанавливаются; MPD слушает только ожидаемый интерфейс.
14. Стабильность: после smoke/manual gate — 24 ч плеерного burn-in по QA-PLAN с 0 неожиданных reboot/OOM/XRUN/user D и сохранёнными логами; shell/X — отдельные короткие supervised циклы, не непрерывный X soak.

## Ближайший порядок действий

1. Сначала сверить состояние дерева и актуальные изменения; сохранить/проверить известный-good boot и доступный rollback. Не менять работающий телефон ради «чистого старта».
2. На устройстве в текущем режиме снять read-only baseline и `uname -a`/`boot_id`;
   сейчас активен shell (X + graphite-shell), плеер — fallback. Выполнить только
   согласованный smoke, сохранить артефакты.
3. На хосте принять P0 #2–7 небольшими изолированными изменениями; после каждой интеграции — build и preview, затем один управляемый deploy владельцем.
4. Не менять одновременно shell, kernel/power и USB gadget. Проверка на устройстве: одна группа изменений за maintenance window, сначала короткий smoke, затем ручной чек-лист.
5. При любом reset/зависании: не повторять сценарий; забрать `last_kmsg`, `dmesg`, boot_id и QA-логи, вернуться к известному-good по согласованной процедуре.
6. После P0 smoke/manual PASS — отдельная 24-часовая плеерная QA-сессия. Только затем выбрать с владельцем release boundary и начать Reader S0/P1.
7. Не проводить сейчас pan/video, panel blank/suspend, USB mode switch, GPU open/ioctl или modem/EFS запись. Это отдельные решения и окна риска, а не обычная проверка работающего устройства.

## Три главных вывода

1. **Уже есть живой shell и проверенные приложения, но есть прототип, а не пройденный release gate.** Сначала воспроизводимый baseline и smoke, затем UX-края и безопасность.
2. **Не смешивать продуктовую работу с экспериментами железа.** USB, modem, video, GPU и panel power имеют отдельные ворота; сейчас не трогать телефон этими проектами.
3. **Стабильность важнее ширины фич.** Один понятный контракт shell/apphost, рабочий ввод и файловые сценарии, подтверждённый QA — после этого читалка; тяжёлые P2 только по явному решению владельца.
