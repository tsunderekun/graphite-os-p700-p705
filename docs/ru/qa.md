# План тестирования и стабильности

План охватывает загрузку, интерфейс, внешние приложения и длительную проверку LG P700. Пороговые значения и критерии ниже описывают план, а не утверждение о прохождении тестов.

## 1. Цель, границы, допущения

### 1.1. Что проверяем
- загрузку и базовые сервисы (pmOS, SSH/RNDIS, Wi-Fi, MPD, `lgjack`, SD);
- fb-плеер: 4 экрана, очередь, темы, настройки, клавиши, лок, питание;
- X11/десктоп: `session-desktop`, Xorg на fbdev, `fbpan-ng`, openbox/tint2,
  приложения, длинная сессия, отсутствие D-состояний и ребутов;
- graphite shell — по критериям `<shell-doc-dir>/OS-DEV-HANDOFF.md` §9 и
  `SCREENS.md` (помечено `N` — ещё не реализовано, тесты станут приёмочными);
- сеть, SD, звук/наушники, питание, память, температуру/ток;
- процедуры прошивки, бэкапа, отката и распознавания «кирпича».

### 1.2. Вне области
SIM/звонки (`SIM busy`), Bluetooth (`hci_smd`), GPS (`GPSNMEA`), камера, EQ
(заморожен) — это известные блокеры, не регрессии. Их проверяем только на
«не стало хуже» (dmesg/процессы), не включаем в приёмку.

### 1.3. Зафиксированный стенд (перепроверить `smoke.sh`)
| | |
|---|---|
| Устройство | LG Optimus L7 P700 (u0), MSM7227A, 1 ядро 1 ГГц, 400 МБ |
| Ядро | `3.4.0-CM #23-postmarketOS`, патчи `msm_fb` 0001/0002 |
| Экран | 480×800, RGB565 16 bpp, `/dev/fb0`, панель перевёрнута (180°) |
| Boot | `/dev/mmcblk0p9`; текущий `artifacts/boot-rot.img` (MD5 `F5C3D546D214E2F5CA3857F7C0CB04E8`, 8 093 696 Б) |
| Откат | `artifacts/boot-rot-KNOWN-GOOD-r14.img` (MD5 `73730BFD117B1EA1BA7CA4FF07FF2100`, 8 138 752 Б) |
| SD | `/dev/mmcblk1p1`, vfat, UUID `<sd-uuid>`, `/media/sd` |
| Сеть | RNDIS `<RNDIS-IP>` (управление), Wi-Fi `<device-ip>` (объект теста) |
| Доступ | `user`/`<device-password>`, sudo `<device-password>` |
| Режим | `/etc/lgtest-mode` = `player`; альтернатива `desktop`; `shell` — план |

**Расхождение, которое надо закрыть до приёмки:** `notes/SYSTEM-STATUS.md`
называет ядро `#22`, `DESKTOP-STATUS.md` — патчи `#23`. `smoke.sh` печатает
`uname -v` и предупреждает, если это не `#23`; для приёмки — `--expect-kernel 23`
(жёсткий FAIL). Все результаты без зафиксированного `uname -a` недействительны.

### 1.4. Принципы
1. **Сначала baseline, потом пороги.** Абсолютные числа ниже — стартовые;
   после первого 30-минутного baseline их надо уточнить и записать в отчёт.
2. **Стабильность = отсутствие ребутов, user-space D, блокировок fb и OOM.**
   `loadavg` на этом устройстве недостоверен: RPC-клиенты дают 8–20.
3. **Один тяжёлый эксперимент за раз.** Не мешать burn-in, `test-x.sh`,
   прошивку и смену режима.
4. **Каждое изменение — с маркером.** `mark.sh "..."` + время в отчёте.
5. **Артефакты важнее слов.** PASS без `summary.txt`/логов не считается.

## 2. Матрица тестов

Обозначения:
- **P** — приоритет: P0 блокирует приёмку, P1 важен, P2 желателен.
- **Как**: `A` — скрипт, `S` — скрипт + ручная проверка, `M` — вручную,
  `N` — ещё не реализовано (тест на будущую оболочку).

## 3. Автоматизация

### 3.1. Схема
```
Windows (.)
  <qa-dir>/host/qa.py  ── SSH (RNDIS <RNDIS-IP>) ──┐
  <qa-dir>/host/qadiff.py                            │
                                                     ▼
                                      <device-qa-dir>/{smoke,burnin,collect,probe,latency}.sh
                                                     │
                                      /var/log/qa/  (артефакты)
                                                     │
                                      tar.gz / SFTP ─┘ → artifacts/qa/
```

  зависеть от объекта теста.

  (грабли PowerShell: `"a|b"` превращается в пайп).
- `qa.py` делает `sudo -S` неинтерактивно, пароль из `LGP700_PASS`.

### 3.2. Что уже автоматизировано

### 3.4. Ключевые проверки и как они устроены
**Порты.** Разбор `/proc/net/tcp` (hex): `0100007F:19C8` — MPD на loopback,
`00000000:19C8` — FAIL (наружу). `:0016` — SSH.

**D-состояния.** Перебор `/proc/[0-9]*/stat`, state `D`; классификация:
- `known` — `krmt_storagecln`, `krtcclntd`, `kbatteryclntd`, `khsclntd`,
  `kadaptiveup`, `klulzactiveup` (RPC/губернаторы, baseline; `comm` может быть
  обрезан до `krmt_storagecl` — учтены оба варианта);
- `user` — `lp7player`, `mpd`, `lgjack`, `Xorg`, `fbpan-ng`, `dropbear` →
  немедленный FAIL + стек;
- `kernel` — любой другой D: 3 сэмпла подряд → FAIL.
`loadavg` только логируется, не является критерием.

**dmesg.** Категории (регистронезависимо):
`panic|Oops|kernel BUG|Unable to handle kernel...`; OOM; EXT4/MMC; display
(`mdp_disable_irq_nosync`, `multiple power-off request`, `chip_lcd_off`,
`lcd_on START`, `esd_int`); audio (`underrun|xrun`); WLAN; SMD/RPC.
Счётчики сравниваются с baseline старта; уменьшение = кольцо перезаписалось,
это не «выздоровление».

**Скриншоты.** `dd if=/dev/fb0 of=... bs=960 count=800` = 768 000 Б,
RGB565, поворот 180°. Все чтения — в фоне с `timeout 8–10`; первый таймаут =
`FB_BLOCKED`, съёмка прекращается. `qadiff.py` считает max-channel delta,
маски и bbox; пресеты `player`, `lock`, `shade`, `queue`.
Baseline — только с устройства, не дизайн-рендеры.

**Отклик.** `latency.sh`:
- pause → стабильный кадр → `mpc next` → опрос кадра каждые 300 мс;
  это end-to-end «MPD изменил состояние → пиксели на экране»;
- старт плеера: kill → запуск `settings` → время до pid и до смены кадра;
- X: запуск `xterm` → время окна; 6 с счётчик изменений кадра (прокси fps).
Точную латентность **тапа** так не измерить (см. §3.6).

**Watchdog.** `qa.py watch` каждые 30 с:
- `probe.sh` (uptime, boot_id, pid/RSS, MPD, память, D, dmesg, сеть, АКБ);
- засекает `boot_id`: смена → `REBOOT`, фиксирует downtime, тянет
  `collect.sh --shot` и `last_kmsg`;
- TCP:22 открыт, но команда висит → `SSH_HANG`; TCP закрыт → `DOWN`;
- `D_BAD`, `DM_CRIT`, память < 20 МБ → отдельные события;
- JSONL + сводка p50/p95/max задержки SSH.

### 3.5. Ограничения и как их обходить
1. **Плеер читает фиксированные `event0/1/5`.** uinput создаёт новый узел —
   плеер его не увидит. Поэтому тап/свайп/лок/джек автоматизируются только
   через:
   - `mpc` (смена трека/пауза/громкость/seek) — проверяет реакцию UI;
   - запуск плеера с аргументом (`queue/info/settings/lock/confirm`) —
     проверяет отрисовку экранов;
   - ручной чек-лист (§3.6).
   Для точной латентности тапа — QA-сборка `lp7player` с
   `clock_gettime` на input/pan (временный бинарник в `/tmp`, не в прошивке)
   или съёмка на камеру 120–240 fps.
2. **fb-чтение опасно.** Никаких циклов `dd` без timeout; при `FB_BLOCKED`
   не повторять, собрать `collect.sh`, перезагрузить.
3. **`MemAvailable` нет** — используется оценка; в отчёте писать
   `avail_est`, не путать с `MemFree`.
4. **`mpc seek %` зависит от версии mpc** — в скрипте есть fallback `+10`.
5. **Время.** RTC может уезжать; интервалы считаются по `/proc/uptime`,
   в CSV есть и epoch, и uptime.

### 3.6. Ручной чек-лист (обязателен, скрипты его не заменяют)
Выполняется до и после 24-часового прогона, 10–15 минут:
- [ ] тап по обложке/полосе/транспорту — подсветка и действие;
- [ ] свайп seek, отпускание, возврат;
- [ ] Vol± коротко/удержание, Power коротко/длинно, HOME;
- [ ] лок: тап, свайп 60, свайп 120, автогашение 15 с;
- [ ] диалог выключения: отмена и подтверждение (потом загрузиться);
- [ ] вставить/вынуть наушники 3 раза на ходу;
- [ ] сменить тему туда-обратно, проверить после ребута;
- [ ] открыть очередь на текущем, проскроллить, тап по строке;
- [ ] проверить Info с треком без тегов и с длинным путём;
- [ ] (X) xterm ввод, pcmanfm, dillo, Home/фокус;
- [ ] (X) 10-минутная сессия, затем `collect.sh --label after-manual`.

## 4. Burn-in 24 часа

### 4.1. Цель и гипотезы
Проверить, что плеер и система переживают сутки непрерывного воспроизведения
и периодических UI-сценариев без:
- случайных ребутов (в т.ч. без АКБ под X — отдельный supervised-тест);
- user-space D и блокировок fb;
- утечек памяти/OOM на 400 МБ;
- деградации звука (XRUN), сети (флапы), SD (ошибки).

### 4.2. Предусловия
- `smoke.sh --strict --require-playing` PASS, `collect.sh --label pre` снят;
- АКБ > 60 %, зарядка подключена (USB 5 В, желательно 1–2 А);
- SD с музыкой, очередь MPD ≥ 8 треков (иначе WARN), repeat включается
  скриптом и восстанавливается в конце;
- управление по RNDIS проверено; Wi-Fi — объект теста;
- нет запущенного `test-x.sh`, прошивки, смены режима;
- известный-good boot-образ и MD5 записаны (на случай отката);
- `boot-capture.start` установлен (опционально, но крайне желательно).

### 4.3. Что гоняем
| Время | Действие |
|---|---|
| 0:00–0:10 | прогрев: play, volume 40 (20 с наушниками), baseline dmesg/D/память |
| каждые 60 с | sample: uptime, boot_id, CPU, память, RSS, MPD, ALSA, h2w, Wi-Fi, ping, D, dmesg, АКБ |
| каждые 10 мин | playback cycle: next / volume / seek 30 % / pause 3 с / seek 70 % / volume mid |
| каждые 2 ч | screen sweep: `queue` → `info` → `settings` → `lock` → `confirm`, по 60 с, кадр на каждом |
| каждые 2 ч (X) | app sweep: xterm → pcmanfm → dillo по 12 с, один за раз, проверка окна/памяти/D |
| 12:00 (вручную) | `mark.sh "jack in"` → вставить наушники → 2 мин → `mark.sh "jack out"` → вынуть |
| 23:50–24:00 | финальный smoke + `collect.sh --label post` + ручной чек-лист |
| всё время | host `watch` каждые 30 с, RNDIS |

`burnin.sh` сам:
- перезапускает плеер, если он умер (счётчик, максимум 12);
- перезапускает MPD/lgjack не чаще раза в 5 минут;
- восстанавливает `next`/pause, если очередь встала;
- при Wi-Fi down 3 сэмпла — reassociate + udhcpc, считает это FAIL;
- останавливается при user-space D, temp ≥ 50 °C, памяти < 12 МБ,
  Xorg/fbpan down, > MAX_RESTARTS.

### 4.4. Что считается провалом
| Событие | Порог |
|---|---|
| Неожиданный ребут | 1 — уже FAIL (собрать `last_kmsg`) |
| Panic/oops/BUG/OOM/EXT4/MMC error | любое новое |
| User-space D (`lp7player/mpd/lgjack/Xorg/fbpan`) | любое |
| `FB_BLOCKED` (таймаут чтения кадра) | любое |
| ALSA `XRUN` | любое |
| Память `avail_est` | < 20 МБ FAIL, < 50 МБ WARN |
| RSS плеера | рост > 10 МБ/ч после прогрева |
| CPU | ≥ 90 % три сэмпла подряд |
| Температура АКБ | ≥ 50 °C — стоп |
| Wi-Fi | 100 % loss 3 сэмпла, нет восстановления 10 мин |
| MPD | down/не играет 3 сэмпла, рестарт не помог |
| SD | ошибка чтения/монтирования |
| Screen sweep | плеер умер/не вернулся, кадр не снят |

### 4.5. X-сессия: отдельно и supervised
24 ч X **не гоняем**: известен ребут под X без АКБ, а fb-дедлок требует
перезагрузки. Вместо этого:
1. `test-x.sh --seconds 600 --xtest` — 10 мин;
2. `test-x.sh --stress --seconds 60` — screensaver/DPMS;
3. живой `session-desktop` 30 мин с `watch`;
4. без АКБ, только USB — 15 мин × 3, с `last_kmsg` после каждого;
5. критерий: 0 ребутов, 0 D, экран обновляется; иначе — ядро/питание,
   не «ещё один прогон».

### 4.6. Ограничения burn-in
- Тач/клавиши/джек не нажимаются скриптом; UI-сценарии — это смена экранов
  через argv + `mpc`, а не реальные жесты.
- Скрипт не видит собственный ребут (процесс умирает); ребут фиксирует
  только host `watch` + `boot-capture.start`.
- `burnin.sh` меняет громкость/трек/повтор; в конце восстанавливает
  состояние, но не точную позицию трека.
- UI-sweep перезапускает плеер (5 экранов каждые 2 ч), поэтому чистый тренд
  RSS одного процесса по 24-часовому CSV не построить. Для утечки — отдельный
  прогон `--no-ui --hours 8` и сравнение RSS.
- Не запускать одновременно с прошивкой и `test-x.sh`.

## 5. Сбор крешей и артефактов

### 5.1. Что забирать и откуда
| Источник | Путь | Когда |
|---|---|---|
| Ядро (текущая загрузка) | `dmesg` | в любой момент |
| Ядро (прошлая загрузка) | `/proc/last_kmsg` | **сразу после ребута**, до следующего |
| pstore | `/sys/fs/pstore/*` | если есть |
| Xorg | `/var/log/Xorg.0.log` | после X |
| Плеер | `/var/log/lp7player.log`, `/var/log/session-player.log` | после старта |
| MPD | `/var/log/mpd/mpd.log` | всегда |
| Наушники | `/var/log/lgjack.log` | всегда |
| Тест X | `/var/log/test-x.log` | после `test-x.sh` |
| Сервисы | `rc-status -a`, `/var/log/messages`, `/var/log/logbookd/*`, `journalctl -b` (если есть) | при разборе |
| Состояние | `/proc/*`, `/sys/class/graphics/fb0/*`, power_supply, switch, asound | при зависании |
| Кадр | `/dev/fb0` (768000 Б) | только guarded, по одному |

`collect.sh` складывает всё в tar.gz и **редактирует** `credential/password/secret`;
`/etc/shadow` и SSH-ключи не копируются.

### 5.2. Порядок после ребута
1. Не перезагружать повторно без нужды.
2. Дождаться SSH (`qa.py watch` сам ждёт, либо `wait_boot`).
3. Сразу: `collect.sh --label reboot --shot` (или `qa.py collect`).
4. Отдельно вытащить `last_kmsg`, даже если tar не собрался:
   `cat /proc/last_kmsg > /tmp/last_kmsg.txt`.
5. Проверить `last_kmsg` на:
   - `PC is at`, `LR is at`, `Call trace`, `Unable to handle` → oops/panic;
   - `No errors detected` + пусто → сброс по питанию/PMIC/watchdog, не panic;
   - шторм `mipi_lg4573b_chip_lcd_off`/`lcd_on` + `mdp_disable_irq_nosync`
     → display/ESD/питание (известный сценарий X без АКБ);
   - `Out of memory`, `mmc1: error`, `EXT4-fs error` → соответствующая ветка.
6. Соотнести время с `events.log` (`mark.sh`) и `watch.jsonl` (downtime).
7. Сохранить: `crash-YYYYmmdd-HHMM-<bootid8>/` + `last_kmsg`, `dmesg`,
   `Xorg.0.log`, `events.log`, `watch.jsonl`, скриншот, заметку.
8. Только после сохранения — решать про откат/перепрошивку.

### 5.3. Если SSH мёртв
- ping RNDIS `<RNDIS-IP>` и Wi-Fi `<device-ip>`;
- если ping есть, а TCP:22 нет — userspace завис (как `hci_smd`): reflash boot
  через fastboot, rootfs не трогать;
- если USB нет вовсе — проверить диспетчер устройств: `18D1:D00D` (fastboot),
  RNDIS, или `QHSUSB_DLOAD` (аварийный режим — стоп, см. §8.5);
- снять фото экрана: это единственный «лог» панели.

### 5.4. Хранение
- На телефоне `/var/log/qa`, при наличии SD — зеркало `/media/sd/qa`
  (не полагаться: SD — объект теста).
- На хосте `artifacts/qa/` (gitignore), хранить 3 последних прогона.
- В git — только текстовые выводы без секретов и без больших логов.
- Для каждого прогона: `meta.txt` (ядро, boot_id, режим, образ, MD5),
  `summary`, `events`, `fails`, сырые CSV, скриншоты.

| `mpc status` | `smoke`/`burnin` | p95 ≤ 200 мс | > 500 мс | > 1 с |
| SSH-команда | `watch` | p95 ≤ 1.5 с | > 3 с | > 30 с / висяк |
| CPU busy (простой) | `/proc/stat` | ≤ 20 % | > 50 % | ≥ 90 % ×3 |
| Loadavg | `/proc/loadavg` | 8–20 (RPC) | > 25 | не критерий |
| D user-space | `/proc/*/stat` | 0 | — | ≥1 |
| D known RPC | то же | 6–12 | > 20 | не критерий |
| `MemFree` | `/proc/meminfo` | > 40 МБ | < 25 МБ | < 10 МБ |
| `avail_est` | Free+Buffers+Cached | > 80 МБ | < 50 МБ | < 20 МБ |
| RSS плеера | `/proc/<pid>/statm` | ±2 МБ/ч | +5 МБ/ч | +10 МБ/ч |
| OOM | dmesg | 0 | — | ≥1 |
| Температура АКБ | `power_supply/battery/temp` | 25–40 °C | ≥ 45 °C | ≥ 50 °C (стоп) |
| Ток/напряжение | `current_now`/`voltage_now` | логировать | — | просадка относительно baseline* |
| ALSA XRUN | `pcm0p/sub0/status`, dmesg | 0 | — | ≥1 |
| Wi-Fi loss | ping шлюза | < 2 % | > 20 % | 100 % ×3 |
| Wi-Fi флапы | `wpa_state`/operstate | 0 | > 2/ч | нет сети 10 мин |

| Длительность X | сессия | 30 мин | — | ребут/D/чёрный экран |
| Кадры X | счётчик изменений | ≥ 5/с при тексте | < 3/с | 0/с |
| Скриншот-дифф | `qadiff.py` | 0 | > 0.3 % | > 0.5 % (masked) |
| Зомби | `ps stat` | 0 | ≥1 | — |

\* Напряжение/ток доступны не всегда; при снятой АКБ метрики нет —
тогда только ребуты/`last_kmsg` и внешний USB-тестер.

### 6.2. Как получить baseline
1. 30 мин в рабочем режиме, без экспериментов.
2. `burnin.sh --minutes 30 --no-ui --label baseline` → CSV.
3. `latency.sh --iters 10` → p50/p95.
4. `smoke.sh --shot`, 3 кадра каждого экрана → `qadiff` (0).
5. Записать в отчёт: ядро, boot_id, температуру, средний CPU, RSS, `mpc_ms`,
   ping loss, SD speed. Все последующие пороги — относительно этих чисел.

### 6.3. FPS и латентность тапа — честно
- Плеер перерисовывается ~1 Гц (state poll) и по событию; «fps» как у
  анимации у него нет. Метрика — «время до смены кадра после `mpc next`».
- X с `fbpan-ng` 10 Гц, но панораматор change-driven: в простое 0 кадров.
  Метрика — изменения кадра при заведомо меняющемся тексте (`xterm`),
  ожидание ≥ 5/с.
- Латентность **тапа** измеряется только инструментированной сборкой или
  камерой; uinput для плеера не работает (фиксированные event-узлы).

## 8. Процедуры: прошивка, smoke, откат, «кирпич»

### 8.1. До прошивки (бэкап)
```sh
# на телефоне, root; SD смонтирована
mkdir -p /media/sd/backup
dd if=/dev/mmcblk0p9 of=/media/sd/backup/p9-boot-$(date +%Y%m%d-%H%M).img bs=1M
md5sum /media/sd/backup/p9-boot-*.img
tar --no-same-owner -czf /media/sd/backup/etc-$(date +%Y%m%d-%H%M).tgz /etc
tar --no-same-owner -czf /media/sd/backup/bin-$(date +%Y%m%d-%H%M).tgz /usr/local/bin
cat /proc/cmdline > /media/sd/backup/cmdline.txt
uname -a >> /media/sd/backup/cmdline.txt
apk info -v > /media/sd/backup/apk.txt 2>/dev/null
sync
```
- Скачать образ на хост и **сверить MD5** (`qa.py pull`, `get_phone.py` или
  `scp`). Без сверки бэкап не считается.
- Проверить: АКБ > 50 %, кабель/порт, старый `fastboot.exe` (157 КБ),
  драйвер `android_winusb.inf`, образ `boot-rot.img` и его MD5.
- Остановить burn-in/`test-x.sh`, дождаться завершения sample.
- Записать в журнал: дату, образ, MD5, команды, кто/что.

### 8.2. Прошивка
Основной путь — старый fastboot:
```
fastboot devices                 # должен показать устройство
fastboot flash boot boot-rot.img # sending/writing ... OKAY
fastboot reboot
```
- Новый fastboot виснет на `Fetching super` — не использовать.
- Если Windows видит `VBoxUSB` — переустановить драйвер (не fastboot).
- Альтернатива с живой системы:
```sh
dd if=/tmp/boot-rot.img of=/dev/mmcblk0p9 bs=1M conv=fsync
sync
# проверка чтением (8 МиБ)
dd if=/dev/mmcblk0p9 bs=1M count=8 2>/dev/null | md5sum
```
MD5 чтения должен совпасть с MD5 образа (с учётом размера раздела; если
раздел больше образа, сравнивать первые `len(img)` байт).
- Не прошивать при низком заряде; не трогать p20/прочие разделы.

### 8.3. После прошивки (smoke)
1. `qa.py wait-boot --timeout 240` (или `wait_boot.py`).
2. `qa.py smoke --shot --strict --require-playing` → PASS.
3. `uname -v` содержит `#23`; `cmdline` не изменился.
4. `dmesg | grep -i 'frame start'` пусто; `grep -c 'MDP IRQ term'` = 0.
5. `test-x.sh --seconds 600 --xtest` (проверить, что на телефоне версия с
   `timeout 3 xdpyinfo`), затем `test-x.sh --stress --seconds 60`.
6. `burnin.sh --minutes 60 --no-ui` (короткий), затем полный 24 ч.
7. Снять новые baseline-кадры и сравнить с эталоном.

### 8.4. Откат
- Система жива: `dd` известного-good образа в p9 → `sync` → `reboot`;
  после загрузки — `smoke` + `uname`.
- Система не грузится, fastboot есть: `fastboot flash boot
  boot-rot-KNOWN-GOOD-r14.img` → `fastboot reboot`.
- Система не грузится, fastboot нет: проверить драйвер/порт/кабель; если
  устройство в `QHSUSB_DLOAD` — стоп (см. ниже).
- Rootfs не трогаем: откат ядра полный, настройки/музыка остаются.

### 8.5. Триаж «кирпича»
| Симптом | Диагноз | Действие |
|---|---|---|
| Логотип LG циклично, SSH через 60–90 с есть | boot/rootfs живы, сессия/сервис | `collect`, `smoke`, `restore-player`, проверить режим |
| Чёрный экран, SSH есть, плеера нет | сессия упала | `session-player`, лог; при D — ребут |
| Ping есть, TCP:22 нет | userspace завис (как `hci_smd`) | reflash boot через fastboot; rootfs не трогать |
| USB нет, fastboot `18D1:D00D` | bootloader жив | старый fastboot, flash boot |
| USB `QHSUSB_DLOAD`/9008 | аварийный режим | **стоп**, не стирать разделы; нужен QPST/сервисный образ, вне текущего инструментария |
| Fastboot висит на `Fetching super` | новый fastboot | старый 157-КБ, драйвер, другой порт |
| Windows `VBoxUSB` | USB захвачен VirtualBox | переустановить драйвер `android_winusb.inf` |
| Устройство греется, ребуты | питание/АКБ/ESD | только USB 5 В 1–2 А, `last_kmsg`, X не гонять без АКБ |

### 8.6. Правила maintenance-окна
- Один эксперимент за раз; перед прошивкой — пауза burn-in.
- Все команды — в журнал (дата, команда, результат, артефакт).
- Не менять `/etc/lgtest-mode` и не пересобирать initramfs в том же окне,
  что и прошивка (сначала проверить ядро отдельно).
- После любого сбоя — `collect.sh` **до** повторной перезагрузки.

## 11. Три главных вывода

1. **Здоровье этого устройства нельзя мерить loadavg.** Известные
   RPC-клиенты в D дают 8–20 при живом CPU. Приёмка должна опираться на
   `boot_id` (ребуты), `last_kmsg`, user-space D, блокировку fb, OOM, XRUN и
   отклик; loadavg — только справочная величина.

2. **24-часовой unattended burn-in возможен только для плеера и только с
   watchdog по RNDIS.** X без АКБ уже давал случайный ребут, а fb-дедлок
   лечится лишь перезагрузкой; длинную X-сессию гоняем короткими
   supervised-прогонами после ядра/питания, а не «сутки и посмотрим».

3. **Автоматизация упирается в фиксированные evdev-пути плеера.**
   Тач/клавиши/джек/лок — ручной чек-лист; всё остальное (MPD, экраны через
   argv, сеть, SD, память, dmesg, скриншоты, ребуты) автоматизируется.
   Точную латентность тапа даёт только инструментированная сборка или
   камера, а не uinput.
